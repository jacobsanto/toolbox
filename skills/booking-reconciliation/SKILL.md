# Booking Reconciliation & Calendar Builder

This skill captures the exact method developed for Arivia Villas (7 villas, Santorini) to turn messy multi-channel booking exports into one trustworthy financial table and two deliverables: an Excel workbook and a visual HTML calendar. Reuse this whole pipeline for other properties/portfolios — only the villa list and any channel-specific receipts change.

## 0. Before starting — ask/collect

1. The channel-manager master export (e.g. Guesty CSV: LISTING, GUEST, CHECK-IN, CHECK-OUT, NIGHTS, CONFIRMATION CODE, STATUS, TOTAL GUEST PAYOUT, SOURCE, RESERVATION ID, CHANNEL RESERVATION ID). This is the backbone — it already has (approximate) villa assignment for every channel. **Trust its unit/listing assignment and its TOTAL PAYOUT / ACCOMMODATION FARE fields (net and pre-commission-gross respectively verified exact against 5 live-checked bookings on Arivia) — but never trust any of its commission fields (e.g. CHANNEL COMMISSION).** On Arivia that field mismatched the real live-verified commission in all 5 cross-checked cases, sometimes showing €0 for a booking with real commission >€200 — the owner explicitly instructed to ignore it entirely and rederive commission from the live per-channel source instead (§2).
2. Booking.com extranet export (.xls) if available — this is the ONLY channel export that natively contains real gross price + real commission amount per booking (columns: Book number, Guest name(s), Check-in, Check-out, Status, Price, Commission %, Commission amount, Payment status, Unit type, Duration).
3. Any raw per-channel exports (Airbnb CSV, TravelNest PDF/CSV, Agoda, etc.) to cross-check the master export for missing/mislabeled rows.
4. List of unit/villa names and every variant spelling seen in the exports, so they can be canonicalized (see §2).

## 1. Data-quality passes — always do these before computing money

- **Villa name canonicalization**: source files spell the same villa many ways ("Anca VIlla", "Villa Anca with pool by Arivia Villas", "Anelia Villa / Anelia Villa w/ Free Parking & Kitchen"). Build a mapping dict → canonical name ("Villa Anca") and apply it everywhere before merging.
- **Cancelled vs no-show vs paid**: a channel manager's normalized STATUS field often collapses "no_show" into the generic cancelled bucket and can show a wrong (zero or stale) payout. For Booking.com specifically, cross-check every cancelled/no-show row against the extranet .xls's own `Payment status` column — only trust an amount as real revenue if that column is filled in. `no_show` is a distinct status from `cancelled_by_guest` and can still be paid.
- **Unpaid cancellations must be zeroed**, even if the master export shows a nonzero payout for them — the extranet/source file is authoritative.
- **Missing/mislabeled channel rows**: cross-reference each channel's own raw export (e.g. a TravelNest PDF) against the master export by guest name + dates. Channels sometimes get mislabeled as `manual`/`direct`, or are missing from the master export entirely and must be added back in.
- **Multi-unit "combo" bookings**: some channels (esp. Booking.com) let a guest book multiple units in one reservation (comma-separated "Unit type" field). Split into one row per unit with price/commission divided proportionally across units, and flag the row (e.g. `multi_villa=True`) so it's visible in the workbook.
- **Double-booking / overlap check**: for every unit, sort confirmed+paid bookings by check-in and check for date overlaps within the same unit. Overlaps usually mean one booking has the wrong unit assigned in the channel manager (classic failure mode: two bookings for the same guest-like name/dates land in different units with different amounts — cross-check ref codes and amounts, and ask the property owner which one is correct before editing). Always verify against the *raw* channel-manager export, not just your merged table, and quote the exact rows you found.
  - **Run this check on calendar-day granularity, not raw timestamps.** Different sources store times inconsistently — a real checkin/checkout time (e.g. 14:00/11:00 from Guesty/Airbnb) next to a date-only source that defaults to midnight (00:00, common for Booking.com-derived timestamps) produces dozens of false-positive "overlaps" that are really just same-day turnovers. Normalize both check-in and check-out to midnight (`.dt.normalize()`) and only flag a pair if `min(checkoutA, checkoutB) - max(checkinA, checkinB) > 0` whole days. On Arivia the raw-timestamp version of this check produced 25 "overlaps"; the date-normalized version correctly reduced that to the 9 that were real.
  - **This check is the single most reliable arbiter of unit assignment — more reliable than cross-referencing raw per-channel exports by name.** On Arivia, several unit corrections made earlier in the same session by cross-referencing 2–3 independent per-channel exports (§7, "same unit mixed up across channels") turned out to be wrong once the overlap check ran — the exports agreed with each other but were all wrong. Always run the full-dataset overlap check as a final pass after any batch of new bookings or unit corrections, not just once at the start, and re-run it again after resolving any overlaps it finds (a fix for one pair can occasionally reveal or resolve another).
  - When presenting an overlap to the owner for resolution, don't guess which side is wrong — quote both bookings (guest, channel, dates, amount, ref) and ask directly which unit each one really belongs to. Apply the owner's answer, then immediately re-check that unit's date range for any newly-introduced conflict before moving to the next pair.
- **Coverage-window check, per channel — do this explicitly, don't assume**: after merging, group by channel and print `min(checkin)`/`max(checkin)`. If one channel's earliest date is weeks later than the others (e.g. Booking.com/Airbnb start in April but TravelNest/Expedia/Direct/Website only start in June/July), that is a strong signal the channel's export simply didn't cover the start of the season — not that the channel had no early bookings. This exact pattern happened repeatedly on Arivia: the first Booking.com extranet file only covered from late June onward (fixed by importing a second wider-range export), and the first Airbnb export was missing ~20 confirmed bookings from April–June (fixed by importing a fuller "101 reservations" export). Always ask the owner for a full-season export per channel rather than trusting whatever date range the first file happens to cover, and flag any channel whose date range still looks truncated after ingestion.

## 2. Per-channel gross / commission / net methodology

Only mark a channel's commission figures as "real" in the workbook notes if they came from an authoritative per-booking source. Never silently blend estimated and real figures without labeling which is which.

| Channel | Method | Source of truth |
|---|---|---|
| **Booking.com** | Use the extranet .xls directly: `Price` = gross, `Commission amount` = commission, gross − commission = net. | Extranet export (real, per booking) |
| **Airbnb** | Export/CSV usually gives only "Earnings" (net, host payout). Formula: `Gross = Earnings ÷ (1 − servicefee%)`, `Commission = Gross − Earnings`. **Verify the fee % is real** by opening 3–5 individual reservations in the host's Airbnb account (Menu → Earnings → Upcoming/Paid → click a "Home" row) and reading the breakdown (`Accommodation`/`Earnings`, `Service fee`, `Taxes`, `Subtotal`, `Total`). If the fee is a consistent flat % across bookings (it was exactly 15.5% for Arivia, confirmed to the cent on 4 separate reservations), the formula is exact, not an estimate — say so explicitly in the notes. Note: "Taxes" on Airbnb is often paid out as a **separate "Pass Through Tot" transaction**, not part of the "Home" total — don't double count it. |
| **Expedia / Hotels.com / VRBO** | Pull the real per-booking "Payment details" breakdown from Expedia Partner Central (apps.expediapartnercentral.com → Reservations → open each reservation) or from a pasted payment-details receipt: `Nightly rates − Promotion − Accelerator` = gross (pre-commission), `Amount retained by Expedia Group` = commission, `Your total payout` = net (this already includes hotel-liable tax). **Partner Central hosts more than one brand** — the same reservation list can contain bookings actually sold under Expedia, Hotels.com, Expedia Affiliate/B2B network, *and* VRBO (all Expedia Group brands); the brand shown at the top of each reservation's detail page (e.g. "uk.Hotels.com", "www.vrbo.com", "B2B distribution network") is the real channel, not whatever the export file's name or a confirmation-number-prefix heuristic (e.g. "EXP-" vs numeric) suggests. Don't assume a combined "Expedia+Hotels.com" export contains only those two channels — open each reservation and read the actual brand line; on Arivia this method plus a Guesty listing cross-check reclassified 2 of 10 new bookings as VRBO that a naive read of the source file would have called Expedia/Hotels.com. Same math applies regardless of brand. | Partner Central (real, per booking) — browse it live; if the owner already has the page open in their own browser, use a read-only screen-share (computer-use tool granted at "read" tier for the browser app) so the owner navigates and you just read the screen, rather than trying to attach the automation extension to their existing tab (it can only drive tabs it opens itself). Never enter credentials. |
| **TravelNest** | Get the real fee structure from one actual payout receipt (rental value → non-refundable-rate discount → channel commission % → TravelNest fee % , both fees computed on the discounted base). Derive a formula from that receipt (for Arivia: 10% discount, then 15% channel + 5% TravelNest fee on the discounted amount → `Gross = Net ÷ 0.80`, `Commission = Gross − Net`) and apply it to all TravelNest bookings. | One real receipt, formula applied to the rest |
| **Agoda** | If there is no extranet/YCS access yet, do NOT invent a commission — show gross = net with commission blank/0 and say plainly in the notes that Agoda commission data is missing, pending access. If the owner has YCS (ycs.agoda.com) access, verify **live, booking-by-booking**: open each reservation in the extranet and read "Reference sell inclusive" as the real amount. Do NOT trust an Agoda CSV export for amounts — the standard Agoda "booking report" CSV export contains no price/amount column at all (only property, dates, guest, party size), so a live browser check is the only way to get real Agoda figures. On Arivia every one of 6 live-checked Agoda bookings differed from what the channel-manager export had on file (one had a straight duplicate entry, one had the wrong unit assigned, others had simply wrong amounts) — treat existing Agoda figures in a channel-manager export as unverified until checked live. | Live YCS extranet, per booking (real) — or flagged as missing if no access |
| **Direct / Website / manual** | No channel commission — gross = net by definition. | — |

## 3. Building the Excel workbook

Structure that worked well (openpyxl, Arial font, `xlsx` skill's `scripts/recalc.py` run after every save even with zero formulas):

- **Σύνοψη (Summary)** sheet: per-unit table (total bookings, confirmed, cancelled, inquiries/expired, gross, commission, net, nights), a per-channel breakdown table below it, and a numbered **notes section** documenting exactly which channels have real vs. formula-derived vs. missing commission data, and any data-quality fixes made (keep this notes section current — it's the audit trail).
- **Master** sheet + **one sheet per unit**: only list bookings that actually counted as revenue (confirmed + paid no-shows) — cancelled/unpaid/inquiry rows are noisy and were explicitly excluded from the detail sheets per owner preference, with their counts still visible in the Σύνοψη totals. Columns: Villa, Κανάλι, Check-in, Check-out, Διαν/σεις, Επισκέπτης, Κατάσταση, Ακαθάριστο (€), Προμήθεια πηγής (€), Καθαρό (€), Κωδικός κράτησης. AutoFilter + frozen header row on every sheet.
- Color-code rows: paid no-show = green, cancelled = pink, inquiry/expired = grey (only relevant if you choose to keep those rows visible).
- Keep the pickle (`master_final_vN.pkl`) as the single source of truth the build script reads from. **When bumping the pickle version, `grep -n "read_pickle" build_script.py` immediately after editing to confirm the path actually changed** — a stale reference here was a real bug that shipped a wrong workbook once.

## 4. Building the visual calendar (HTML artifact)

A CSS-grid Gantt-style calendar (sticky first column = unit names, sticky header = month/day, one row per unit, booking bars spanning `grid-column: checkinCol / checkoutCol`) works well because a single unit can never have overlapping bookings, so no absolute-positioning/collision logic is needed — grid-column/grid-row placement is enough. Key UX pieces the owner asked for after first seeing it:
- Villa filter chips (multi-select + "Όλες/All") to show one, several, or all units.
- Guest search box that dims non-matching bars.
- Hover tooltip with full detail (channel, dates, nights, gross/commission/net, ref).
- **Explicit prev/next navigation arrows** (scroll by ~1 week) and **month quick-jump chips** — a purely scrollable calendar with no arrows/labels reads as "missing" a month even when it's just scrolled off-screen. Always add both.
- "Σήμερα/Today" jump button, auto-scrolled to today's date on load.
- Channel-color legend (one distinct hue per channel).
- Only paid/confirmed bookings by default, consistent with the workbook.
- Publish as a Claude Artifact (self-contained HTML, data embedded inline as JSON) since this is a tool the owner will reopen repeatedly — don't just send it as a one-off file.
- **A "+ Νέο κατάλυμα" button in the header, top-right, on the same row as the H1 title** opens a short instructional modal (not an in-page uploader) explaining that reconciling a new property still happens in a chat with Claude — this was a deliberate decision (see §5a), not a missing feature. Keep this button and modal in every property's calendar.

## 5. Reusing this for another property

### 5a. One property = one separate artifact/calendar (decided with the Arivia owner)

We explicitly considered and rejected building a multi-property switcher inside a single page (tabs/dropdown to flip between properties in one artifact) and rejected fully automating new-property onboarding via an in-page file-drop wizard. Both were rejected for the same reason: reconciling a new property's data requires judgment calls (which villa a mislabeled booking really belongs to, whether a "cancelled" row was actually paid, which channel-commission formula applies) that only get resolved correctly by asking the owner in a conversation — a static page or a fixed JS rule set can't ask that question. Trying to fake it with rules risks silently shipping wrong financial numbers.

**Decided approach**: each property gets its own separate Claude Artifact / link, built the normal way (this whole SKILL.md, run as a conversation). Nothing gets deleted or overwritten in an existing property's page to make room for a new one. When the owner has a new property to onboard, they say so in chat and hand over the files (channel-manager export + per-channel receipts/exports); walk through §0–§4 for that property exactly as done for Arivia, and publish its own new Artifact URL. The owner is fine with ending up with multiple separate links, one per property (they explicitly chose this over a merged single-page switcher when asked, given the tradeoff was explained: separate links means nothing is ever lost/overwritten and each calendar stays simple, at the cost of not having one unified page). If the number of properties grows large enough to be unwieldy, a simple index/landing page listing all property links can be built later — but do not build that pre-emptively.

### 5b. General reuse steps

1. Repeat §0–§1 with that property's own exports and unit list.
2. Re-derive each channel's formula/receipt per §2 for that property specifically — commission %/fee structures are not guaranteed to match Arivia's (e.g. the 15.5% Airbnb rate is Arivia's confirmed rate, not a universal constant — re-verify per host account).
3. Reuse the workbook and calendar code structure from §3–§4 as-is; only the villa list, channel list, and any property-specific notes change.
4. Keep a running "methodology" notes section per property — it's what let us safely delete a mis-assigned duplicate booking with the owner's one-line confirmation instead of guessing.

## 6. Suggested subagent / expert breakdown

When running this pipeline for a new property, don't do it single-threaded in one long context — split it across specialized subagents (via the Agent or Workflow tool), each an "expert" in one narrow piece. This mirrors how the Arivia build actually went wrong/right: every bug found (§7) came from one stage silently feeding bad data to the next, so the expert boundaries below are chosen to make each stage independently checkable.

1. **Ingestion & canonicalization expert** — reads every raw export (Guesty/channel-manager CSV, Booking.com extranet .xls, per-channel CSV/PDF exports), builds the villa/unit name canonicalization map, parses every date with its source's correct format *before* any concatenation, and outputs one merged raw table. Does not compute money yet.
2. **Data-quality auditor expert** — takes the merged table and runs the checks in §1: cancelled-vs-no-show-vs-paid cross-check against the authoritative per-channel source, missing/mislabeled row detection (diff each channel's own raw export against the merged table by guest+dates), multi-unit combo-booking splitting, and the double-booking/overlap scan per unit. Reports findings as a list of specific rows with evidence (ref codes, amounts, source lines) — never auto-fixes an ambiguous case, always asks the owner when two sources disagree (as happened with the Ana Colas/Anelia duplicate).
3. **Channel-commission expert(s)** — one per channel family, since the evidence-gathering method is completely different per channel (see §2): a **Booking.com expert** just reads the extranet .xls columns directly; an **Airbnb expert** derives/verifies the service-fee % by opening several real reservations in the host's Airbnb account via browser automation and checking the fee is a consistent flat rate; an **Expedia/Hotels.com expert** pulls real per-booking payment-detail breakdowns from Partner Central via browser automation; a **TravelNest expert** derives the fee formula from one real payout receipt and applies it. Run these in parallel — they're independent of each other and only need the cleaned table from stage 2.
4. **Workbook-builder expert** — takes the fully reconciled table (all channel experts' outputs merged back in) and builds the Excel deliverable per §3: Σύνοψη + Master + per-unit sheets, notes section, AutoFilter/freeze panes, and runs the xlsx skill's recalc check before handoff.
5. **Calendar-builder expert** — takes the same reconciled table and builds the HTML/Artifact calendar per §4 (villa filter, search, tooltip, month-jump/prev-next nav, channel legend).
6. **Verification expert** — final pass: re-derive the per-unit and per-channel totals independently (e.g. a standalone groupby/sum in a fresh script) and diff against what the workbook/calendar actually show, the same way the stale-pickle bug in §7 was originally caught by hand. Only hand the deliverables to the owner after this passes.

Stages 1→2 are sequential (auditor needs clean canonical data); stage 3's channel experts can fan out in parallel once stage 2 is done; stages 4 and 5 can also run in parallel off the same reconciled table; stage 6 gates final delivery.

## 7. Things that went wrong once — don't repeat

- Concatenating date strings from multiple channels (different formats, e.g. Airbnb `M/D/YYYY`) into one DataFrame and parsing dates *after* concatenation silently produced NaT for most rows. Always parse each source's dates with the correct explicit `format=` before merging.
- Treating "no_show" as equivalent to "cancelled" and zeroing a payout that was actually collected.
- Editing a build script's data-source path (pickle version bump) without verifying the `read_pickle(...)` line actually changed — caused a stale/wrong delivered workbook once. Always `grep` to confirm after any such edit.
- **Multi-unit combo bookings had their full price duplicated onto every unit instead of split** — a booking spanning 2–3 units showed the *complete* gross/commission/net on each unit's row, silently double- or triple-counting the same money in the grand total (a €5,717 overcount on Arivia across 4 bookings), even though the workbook's own notes claimed the amount was split. This shipped once before being caught — when adding new combo-booking parsing logic, always verify the *existing* combo rows in the dataset are actually divided (`sum by ref` should equal one shared total, not one full total per unit), not just the new ones being added.
- **The same unit got mixed up in the channel-manager export more than once, across different channels** — not a one-off fluke. On Arivia this happened at least 4 separate times (Ana Colas/Agoda, Jaden Smith/Airbnb, Tina Spezzacatena & Cinzia Fornoni/Airbnb), always the channel manager assigning a booking to the wrong unit while the channel's own native export(s) agreed on the correct one. When a raw per-channel export disagrees with the channel-manager export on which unit a booking belongs to, and especially when 2+ independent raw sources agree with each other against the channel manager, trust the channel-native source(s) — but still surface the conflict and the evidence to the owner rather than silently overriding.
- **A channel-manager's "room type"/rate-plan string does not reliably map 1:1 to a unit, even when it looked consistent for several known bookings.** On Arivia, 4 known bookings suggested a clean mapping ("Superior Villa, Private Pool" → one unit, "Deluxe Villa" → another, etc.), but the exact same room-type string ("Standard Villa, Private Pool, Courtyard View") turned out to belong to two different guests staying in two different units. Never infer a unit from a room-type/rate-plan string alone, even after it seems to hold for several bookings in a row — always confirm against a channel-manager listing-name cross-reference or the owner directly.
- **A guest export can be "confirmed" but still not the full truth of what was paid** — an Airbnb/TravelNest row can show as "Canceled by guest" / "CANCELED" in the export's own status field while its Earnings/Net column is still nonzero, meaning the guest paid despite the cancellation (a no-show-style outcome, not unique to Booking.com no-shows). This happened repeatedly (Peep Raudmann, Youssra Lamkadem, Usha) and is easy to miss if you filter out every row whose status contains "cancel" before checking its payout column — always check the amount column first, independent of the status label.
